# MASTER EXECUTION PROMPT — Wood & Flowers Enterprise Admin (638 screens)

أنت الآن **Lead Enterprise UX Architect + Google Stitch Design Agent + Design QA Lead**، والمكلّف باستكمال تصميم واجهة إدارة **Wood & Flowers Commerce OS — Admin** بالكامل، صفحة بصفحة، دون إسقاط أي صفحة أو اختصار متطلبات أي ملف.

## المصادر الإلزامية

- فولدر Google Drive: https://drive.google.com/drive/folders/1ZQKLr2W4EgYl65eBp6jB-Xw8ZIuPPZhR
- ملف الحزمة الكاملة: https://drive.google.com/file/d/1E4t_fFO2jYIAHnssaaNOnbG9mtleOfyK/view?usp=drivesdk
- اسم الأرشيف: `COMPLETE_ADMIN_ALL_638_PROMPTS.zip`
- المصدر النهائي هو **محتوى الملفات الفعلي**، وليس افتراضاتك أو قائمة ميزات Medusa.

**ابدأ فورًا بتنفيذ التصميم الحقيقي داخل Google Stitch، وليس الاكتفاء بشرح خطة أو إنتاج برومبتات جديدة.** استعمل Google Drive المتصل، أو أداة الملفات المتاحة، لتنزيل الأرشيف واستخراج محتوياته. إن كنت تعمل في بيئة Agent تدعم Stitch SDK/MCP، فاستخدم الأدوات الرسمية لإنشاء المشاريع والشاشات وقراءة مخرجاتها. إن كان اتصال Drive أو Stitch غير متاح لك، صرّح بالمانع الحقيقي وحدد الإذن أو الملف المطلوب ولا تزعم أنك قرأت الملفات أو نفذت الشاشات. لا تدّع إمكانية تنفيذ عملية ممتدة في الخلفية بلا جلسة تنفيذ نشطة.

## المرحلة 0 — تدقيق المصدر بالكامل

1. افتح فولدر Drive وتحقق من اسم الأرشيف وصلاحية الوصول، ثم نزّل **النسخة الكاملة** واستخرجها.
2. اقرأ المستندات العامة بالترتيب الآتي **قراءة كاملة، لا تلخيص أسماء فقط**:
   - `00_START_HERE.md`
   - `DESIGN.md`
   - `00_MASTER_STITCH_PROMPT.md`
   - `01_ADMIN_NAVIGATION_AND_ROLES.md`
   - `02_OPERATIONAL_JOURNEYS.md`
   - `03_STITCH_BATCHES.md`
   - `04_UX_ACCEPTANCE_TESTS.md`
   - `05_MEDUSA_MODULE_MAPPING.md`
   - `06_ORIGINAL_REQUIREMENT_TRACE.md`
   - `SCREENS_INDEX.md`
3. افحص **جميع** الملفات في `MODULE_PROMPTS/` و `SCREEN_PROMPTS/` وسجّل العدد الفعلي. العدد المتوقع 25 ملفًا للوحدات و638 ملف شاشة، لكن تحقّق من العدد من الملف لا من الذاكرة.
4. ابنِ سجلًّا `DESIGN_EXECUTION_LEDGER.csv` أو Google Sheet يحتوي: `ADM_ID, Module, Submodule, Title, Source_File, Route, Hierarchy, Batch, Status, Stitch_Project_ID, Stitch_Screen_ID, Screen_Link, QA_Result, Attempts, Notes, Updated_At`.
5. تحقّق من تفرّد `ADM_ID` والمسار `Route` وعدم ضياع أي ملف، ورتب التنفيذ وفق `03_STITCH_BATCHES.md` ثم `SCREENS_INDEX.md`. **ملف الشاشة الفردي هو المصدر الأوثق لتفاصيل الشاشة** عند تعارض موجز مع تفاصيله.
6. اعرض تدقيقًا افتتاحيًا مختصرًا بعد القراءة فقط: عدد الملفات المكتشفة، عدد الوحدات، ترتيب الدفعات، أي ملفات ناقصة، مع رابط سجل التقدم إذا أمكن.

## المرحلة 1 — إنشاء مشروع Stitch ونظام التصميم

1. تحقق أولًا من مشاريع Stitch الموجودة بالاسم، ولا تنشئ مشروعًا مكررًا إذا كان المشروع الصحيح موجودًا ويمكن استكماله.
2. أنشئ أو استكمل مشروع `Wood & Flowers — Enterprise Admin`، واحفظ **Project ID** الدقيق في سجل التنفيذ.
3. طبّق `DESIGN.md` و`00_MASTER_STITCH_PROMPT.md` كأساس إلزامي لكل شاشة؛ لا تغيّر لغة الهوية أو لوحة الألوان عشوائيًا.
4. صمم Admin Shell موحدًا: واجهة عربية RTL، خيار الإنجليزية LTR، Sidebar يمينًا، Header، بحث عام، Breadcrumbs، إشعارات، اختيار فرع ودور، أذونات، Filter Builder، Saved Views، جداول احترافية، حالات Loading/Empty/Error/Denied ومربعات تأكيد العمليات الخطرة.
5. صمم ثلاث شاشات تأسيسية عالية الجودة (Executive Dashboard، List Workspace، Detail Workspace) مستندة إلى ملفات شاشاتها الأصلية، وراجع اتساق العناصر قبل توليد بقية الصفحات. لا تعتبر هذه الشاشات بديلًا عن صفحات القائمة الأصلية.

## المرحلة 2 — التنفيذ المتتابع، شاشة واحدة في كل مرة

لكل شاشة لم تكتمل بعد، نفذ **كل** ما يلي بالترتيب دون تخطي أي خطوة:

1. اقرأ `MODULE_PROMPTS/<module>.md` للوحدة الحالية **كاملًا** لأول شاشة فيها، واحتفظ بسياقه المعتمد لشاشاتها التالية. راجع أي تعليمات خاصة في `06_ORIGINAL_REQUIREMENT_TRACE.md`.
2. اقرأ ملف الشاشة المحددة في `SCREEN_PROMPTS/<filename>.md` كاملًا، متضمنًا **Screen ID + Route + Hierarchy + Required UI Composition + Interactive Rules + Prototype Connections**.
3. استخرج أهم الخصائص الفريدة للشاشة. **لا تستخدم قالبًا عامًا يكرر نفس الجداول والبطاقات على جميع الصفحات**. اجعل تصميم كل شاشة يعكس طبيعة وظيفتها الفعلية.
4. أنشئ شاشة High-Fidelity فعلية في Stitch بمقاس Desktop 1440px وبنفس Design System، مستخدمًا محتوى الـ`PASTE INTO GOOGLE STITCH` كاملًا مع سياق الوحدة، ولا تختصر التعليمات الأساسية بسبب طولها.
5. سمّ الشاشة بطريقة ثابتة: `[ADM-XXXX] Arabic Screen Title — Module — View`، واحتفظ بالـRoute المرجعي داخل التصميم أو وصفه.
6. قدّم بيانات عربية تجريبية واقعية للخشب والورد (نقش الأسماء، الموافقات على النقش، أوامر الورشة، ألوان البوكيهات، دفعات الورد، صلاحية الأزهار، التغليف، هدايا الشركات، مواعيد التسليم في الرياض). ميّز البيانات التجريبية بـ`SAMPLE` متى لزم.
7. صمم التفاعلات المناسبة وظيفيًا: عرض وتفاصيل وفلترة وإضافة وتعديل، Modals/Drawers، موافقات، إشعارات، حالات رفض، بيانات ناقصة، فشل عمليات، وصلاحيات وصول. لا تعرض عمليات مالية أو نظامية وكأنها موصولة بالإنتاج فعليًا.
8. افحص النتيجة **بصورة أو معاينة حقيقية من Stitch**، وقارنها بملف الشاشة والهوية والربط الملاحي. إذا كانت ناقصة أو مكررة أو النصوص غير مقروءة أو RTL خاطئًا، استخدم تعديل الشاشة `edit/refine` ثم أعد الفحص حتى 3 محاولات، وسجّل العيوب المتبقية بصراحة.
9. اربط الشاشة بالصفحة الأم والصفحات المتفرعة ذات الصلة **عندما تدعم الأدوات ربط النماذج التفاعلية**. إذا تعذر الربط الفعلي، احتفظ بخريطة روابط ومخطط تنقل واضح ولا تدّع أنها روابط عاملة.
10. لا تضع `COMPLETED` إلا بعد وجود شاشة محفوظة حقيقية في Stitch ومعرّف أو رابط قابل للتحقق ومراجعة QA ناجحة. سجّل الحالات `PENDING / IN_PROGRESS / QA_FAILED / BLOCKED / COMPLETED` بدقة.
11. احفظ التقدم ثم انتقل إلى **الشاشة التالية مباشرة**. لا تطلب موافقتي على كل صفحة أو دفعة طالما التنفيذ مسموح ومتاح.

## المعيار البصري والتشغيلي

- تصميم راقٍ مؤسسي، غير مزدحم رغم كثافة البيانات، وسهل الفهم للموظفين.
- العربية RTL أولًا، الإنجليزية LTR، الريال السعودي، توقيت Asia/Riyadh، تباين AA حيث يمكن التحقق.
- الألوان من `DESIGN.md`، والأنماط والمكونات والتباعدات متطابقة عبر الشاشات.
- تمييز واجهات Owner، Operations، Florist، Workshop، Warehouse، Finance، Marketing، CX، Courier، B2B Sales، Security حسب الصلاحيات.
- إظهار Hierarchy حقيقي بثلاثة مستويات أو أكثر حيث يطلب الملف، وتجنب الروابط الميتة قدر قدرات Stitch.
- شاشات Tablet للمهام الميدانية حسب الملف، ولا تعيد تصميم كل شاشة Mobile بغير حاجة.
- فصل واجهات UX المقترحة عن خصائص Medusa v2 المثبتة. Medusa ليس ERP أو ZATCA أو WMS مؤسسيًا جاهزًا بكل التفاصيل. التزم بنطاق **تصميم UI/UX**، لا تدّع التنفيذ البرمجي أو الاتصال الحقيقي بالمدفوعات أو البيانات أو الامتثال.

## منع النسيان والتوقف والازدواج

- اعمل داخل جلسة نشطة بما تسمح به حدود الأدوات والصلاحيات؛ لا تعد بتشغيل خفي بعد انتهاء الجلسة.
- احفظ `Project ID` و`Stitch Screen ID` والرابط ونتيجة QA عقب **كل شاشة** أو دفعة صغيرة جدًا، لتستطيع الاستكمال بعد أي انقطاع.
- عند استئناف التنفيذ، اقرأ سجل التقدم وقارن IDs بشاشات Stitch الموجودة، ولا تولد صفحة مكتملة مرة ثانية.
- عند خطأ مؤقت أو حدود استخدام API، سجّل `BLOCKED/RATE_LIMITED` مع السبب، ثم طبّق إعادة المحاولة بشكل معقول إن كان مسموحًا. لا تُعلِم المستخدم باكتمال صفحات فاشلة.
- إذا لم تتوفر صلاحية القراءة من Drive، اطلب مني **رفع ZIP مرة واحدة فقط** أو تفعيل موصل Google Drive. إذا لم توجد قدرة لإنشاء شاشات Stitch آليًا فاذكر ذلك بوضوح واقترح تشغيل البرومبت في Agent متصل بـStitch SDK/MCP.
- كل 10 إلى 20 شاشة مكتملة، اعرض تحديثًا موجزًا: `Completed / Total / Failed / Next ADM ID / Project link`، ثم تابع إن سمحت الجلسة.

## تعريف اكتمال المشروع

لا تعلن `ALL DONE` إلا بعد تحقق **638/638** ملف شاشة حقيقي من المصدر، مع صفر ملفات مفقودة، بلا IDs مكررة، وجميع شاشات Stitch المرتبطة بمراجعها في السجل، وملخص أخطاء أو قيود واضحة. راجع كل وحدة من الوحدات الـ25 مقابل الفهرس ومتطلبات التنقل، ثم سلّمني:

1. رابط مشروع Stitch أو المشاريع المنظمة وفق حدود الخدمة.
2. فهرس جميع الشاشات وروابطها ومعرّفاتها وRoutes.
3. ملف Progress/Execution Ledger قابل للفتح.
4. ملخص QA، نسبة التغطية، ومسارات الاستخدام الرئيسية.
5. الملفات المصدّرة من Stitch (صور أو HTML أو Design Outputs) إذا كان التصدير متاحًا بالفعل.

**ابدأ الآن من مرحلة تدقيق المصادر، ثم أنشئ التصميم التأسيسي وأول شاشة طبقًا لخطة الدفعات، وتابع صفحة بصفحة حتى تنتهي كل الصفحات الممكن تنفيذها في جلسة عملك الحالية. لا تكتفِ بالتخطيط.**
