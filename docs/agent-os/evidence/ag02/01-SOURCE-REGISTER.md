## 2. Boundaries Between Verified Facts and Working Assumptions

### Confirmed Architectural Facts
1. **Single-Store Self-Hosted Deployment**: CommerceOS is deployed as an independent, self-hosted store per client. There is no multi-tenant database partitioning or `tenant_id` on Medusa core tables.
2. **Medusa Core Invariance**: Modifying files inside `@medusajs/*` in `node_modules` or altering Medusa's internal database migrations is strictly prohibited by Constitution Principle III.
3. **Inventory Authority**: Stock levels and reservations are owned exclusively by Medusa's native `InventoryModule`. Reservations are created automatically within `completeCartWorkflow` upon order placement. No secondary stock balance in Redis or temporary cart TTL reservations exist.
4. **Admin Authentication vs. Authorization Gap**: Medusa v2 core provides authentication for admin users, but does not provide out-of-the-box granular Staff RBAC (e.g. differentiating Admin vs Member roles with granular permissions). Custom authorization middleware is required, and all protected endpoints must remain secure (fail-closed) even during Redis outages.
5. **No Runtime Execution in AG02**: In compliance with the gate rules, no application code, Medusa runtime, or external plugins have been executed in AG02. All assessments represent design literacy and architectural specifications.

### Explicitly Flagged Hypotheses & Target Heuristics
* *Admission Control Under High Load*: If flash sales generate extreme request spikes, an optional Redis-backed HTTP rate limiter / request admission queue may throttle incoming traffic before hitting the database. This is an admission throttle, NOT an inventory balance.
* *Performance Targets*: Targets such as p95 latency < 500ms under high load are non-binding engineering goals that must be validated with real load testing (e.g. k6) in AG06/AG07, not claimed as pre-verified facts.
